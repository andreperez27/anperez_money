## 4. Debug da 42 no SQL Editor (2 erros, ambos meus, corrigidos sem mudar semântica)

- **42P01 no backfill**: o `ON` do `JOIN` referenciava `cm` (tabela-alvo do UPDATE, que não faz parte do `FROM` — proibido no Postgres). Predicados com `cm` movidos para o `WHERE` (+ mesma regra na subquery `NOT EXISTS`); `ON` só com `m.conta_id = cx.conta_id`.
- **23502 nos TESTES**: o SQL Editor roda como `postgres` sem JWT → `auth.uid()` NULL (a linha falha mostrava `user_id` null). Bloco DO agora fixa `request.jwt.claim.sub` para o usuário mais antigo com `set_config(..., true)` — vale só a transação (cobre INSERTs e o `auth.uid()` interno das RPCs, apaga-se sozinho) + assert de sanidade.

## 5. T4 falhou: conta 1050 (esperado 1100) — trigger fazia o trabalho duas vezes

- **Causa raiz**: minha premissa "trigger só dispara em INSERT" estava errada — `03_triggers_editar_excluir_movimentacoes.sql` (FASE 3b) define `trg_atualizar_saldo` como `after insert or update or delete`, com delta em UPDATE e reversão em DELETE. Minhas RPCs faziam UPDATE manual em `contas` **e** atualizavam/apagavam a contrapartida → delta aplicado 2× (1150 − 50 manual − 50 trigger = 1050, exatamente o observado).
- **Correção**: removidos todos os UPDATEs manuais em `contas` das duas RPCs (validações, travas e ajustes em `caixinhas.saldo` mantidos — ali não há trigger); saldo da conta agora só via trigger. `trg_protege_transferencia` verificado: só barra linhas com `transferencia_id` (as nossas têm NULL).
- Re-simulação: T4 edita 100→150 → caixa 150 manual + trigger −50 → conta 1100 ✓; T5 exclui → caixa 0 + trigger +150 → conta 1250 ✓.
